nips优秀论文“写得好”的地方。
一、它们最强的共性：不是“介绍一个方法”，而是“建立一个完整问题闭环”
agent 方向几篇论文的共同点非常明显：都不是只讲一个模块，而是把问题、方法、数据、benchmark、成本、部署价值连成一个闭环。论文更强调 system closure、practicality、benchmark 生态，而且第一页就用大图建立 problem-method-result 的全局印象。OpenCUA 和 Web-Shepherd 也是这个套路：一个是 tool→dataset→pipeline→benchmark→model，全链条打通；另一个是 model + collection + reward benchmark 一起给。
这类写法的好处是，reviewer 不会觉得“你只是做了个小 trick”。他会更容易接受：你解决的是一个真实研究空缺，而且补的是整套 research stack。
二、标题和第一页很会“先声夺人”
这些论文非常会命名。高质量 agent 论文偏爱“短名字 + 冒号 + 功能描述”，比如 G-Memory、Web-Shepherd、OpenCUA、Self-Taught Lookahead。这种命名不是装饰，它直接把卖点塞进名字里：memory、shepherd、open、self-taught，都能立刻唤起功能联想。
同时，它们很重视第一页的信息密度。第一页通常是 Abstract + Figure 1，而且 Figure 1 往往不只是 framework 图，还兼具任务示例、性能 teaser、成本对比等作用。G-Memory 的 Figure 2/整体图结构、OpenCUA 的总览图、Agent Distillation 的概念图、Web-Shepherd 的性能-成本图，都是这种“先用图把贡献讲明白”的典型。
三、Abstract 的优秀点：不空谈，6 句话内把研究价值讲完整
这些论文的摘要有一个很稳定的骨架：
先写场景和重要性，再点出现有系统的硬伤，然后给出方法名和一句定义，再用 (1)(2)(3) 这种格式概括组件，最后给出硬结果和开源资源。
更重要的是，它们的 Abstract 很少写空泛愿景，而是写真实工程瓶颈。比如：
- Agent Distillation 不是说“小模型推理能力不足”，而是具体说 CoT distillation 在稀有事实和精确计算上会 hallucinate，所以要蒸馏 reason-act-observe 行为。
- Web-Shepherd 不是说“web agent 还有挑战”，而是直接说用 GPT-4o 做 verifier 太贵、太慢、还不适合真实部署，所以需要专门的 PRM。
- TMTE 也不是泛泛说多模态图学习难，而是直接列 noisy interactions、missing connections、task-agnostic topology 这三类结构问题。
这种摘要一看就很“NeurIPS 式”：问题不是抽象的，而是明确、可验证、可量化的。
四、Introduction 的优秀点：四段完成“领域定位 → 痛点拆解 → 方法直觉 → 贡献落点”
这批论文的 Introduction 都很讲究节奏。无论 agent 论文还是 graph 论文，本质上都接近四段式。
第一段先把领域背景立住，而且不是只给定义，会顺手举应用，让问题显得值得做。Hou 这篇虽然不是 NeurIPS，但引言也很典型：它不是直接给公式，而是先用 mobile edge computing 和 multi-hop networks 两个例子，把多阶段系统的现实性讲清楚。
第二段最关键：它们不会只写“existing methods still face challenges”，而是把 challenge 拆成几个命名过的 failure modes。graph 风格总结里提到常用 (1)(2)(3) 编号问题，甚至用 L1/L2 标识 limitation；agent 风格总结里也强调，第二段应该明确写出 memory 太粗糙、reward 太稀疏、evaluator 太贵、小模型会 hallucinate、闭源系统难复现这些硬伤。
第三段不是“本文提出一个新方法”，而是会先抛出一个研究问题，或者先给一个核心 insight。graph 风格里常见斜体问题句，像 “How can we adaptively learn ...?”；agent 风格里常见 “a core research question emerges” 或 “a natural question arises”。然后方法名立刻出现，再用 2–4 句把关键机制拆开。
第四段通常非常规整，直接 Our contributions are summarized as follows，并且稳定分成三类：问题诊断/新视角、新方法/新框架/新数据、大规模实验结果。这个点在两个 preference 文件里都高度一致。
五、Method 部分写得好的地方：模块命名清晰，而且每个模块都回答“为什么要有”
这些论文的方法节，不是堆公式，而是模块化非常明确。好的地方主要有三个。
第一，模块标题非常清楚。比如 Insight Graph / Query Graph / Interaction Graph、first-thought prefix、self-consistent action generation、WebPRM Collection，读者只看小标题就能知道每节在干什么。agent 风格总结里明确指出这是一种共性；graph 风格总结也提到 method 小节常采用 [动作/过程] from/via [来源/手段] 这种命名方式。
第二，先讲动机，再讲做法。TMTE 的方法部分就是典型：先说原图拓扑有 noisy 和 missing 问题，所以要从原始模态空间出发演化拓扑；然后再给 multi-perspective metric learning 和 anchor-based approximation。它不是一上来就甩公式，而是先把“为什么需要这一步”讲了。
第三，会把 inference-time usage 写进去。这在 agent 论文里尤其重要，因为性能往往不只来自 training，还来自 test-time orchestration。Agent Distillation 会写 student 推理时怎么做 self-consistent action generation，STL 会写 value model 在 search 里如何替代昂贵 evaluator，G-Memory 会写新 query 到来时如何检索、向上/向下遍历、执行后再更新。
六、Experiment 写得好的地方：不只回答“更强吗”，还回答“更值吗”
这些论文的实验部分几乎都有同一种 reviewer 视角：不仅问性能，还问成本、泛化、稳定性、兼容性。
agent 风格总结里写得很明确：高质量 agent 论文通常同时回答 five questions——是否更强、是否更便宜、是否更稳定、是否更能泛化、是否能 plug into existing frameworks。Web-Shepherd、STL、OpenCUA 都特别重视这一点。
具体来说：
- Web-Shepherd 的亮点不是只有分数高，而是“比 prompted GPT-4o verifier 更强，同时便宜 10x”。
- STL 的亮点不是只有 search performance 提升，而是强调 reward-free、自举训练、并显式做了 compute and cost efficiency、environmental usage、scaling trends。目录里这些章节本身就说明作者非常懂 reviewer 想看什么。
- G-Memory 也不是只说成功率提升，而是同时强调 token cost 可控、plug-and-play。
所以它们实验写得好的根本原因是：指标和论文定位一致。如果论文讲系统或 agent，不谈 cost、token、推理开销，故事就不完整。
七、graph/method 论文那一路的优秀点：结构规整、符号统一、动机和实验耦合得更紧
如果看 TMTE 和 preference.md 这一类材料，它们代表的是另一种优秀写法：更偏 method paper，但仍然很讲故事。
最值得学的是三点。
第一，符号体系高度统一。preference.md 里把图、邻接矩阵、拉普拉斯、特征矩阵、损失函数下标、温度参数、平衡系数都固定下来。这会让整篇论文的数学表达非常稳，不会前后切换写法。
第二，Empirical Study 先行，为方法设计开路。TMTE 很会写的一点，是它不是直接进方法，而是先做 empirical investigation，提出 Q1/Q2/Q3，分析 original topology 不是最优、不同任务偏好不同拓扑、TMTE 更鲁棒，然后再引出为什么要做 topology-modality co-evolution。preference.md 把这种写法总结得很完整。
第三，方法节的层级感非常强。概述段先告诉你本节要讲什么、分别在哪几个 subsection；接着每个 subsection 内还有粗体小模块，比如 similarity learning、scalability、smooth fusion。这样 reviewer 扫一眼就知道结构。
八、这些论文“语言上”具体强在哪里
语言层面，它们有几个共同优点。
一个是转折和推进词使用很稳。However / To address this / To bridge this gap / Concretely / Specifically / Consequently 这些词反复出现，但并不显得空，因为每次都真的在推进逻辑。两个 preference 文件都明确总结了这种连接方式。
另一个是强调方式统一。graph 风格会用粗体小标题、斜体研究问题、Modality → Topology 这种箭头表示因果；agent 风格则更偏用明确模块名、显式贡献列表、场景化 failure case。
还有一个很重要：很少废话。尤其是 agent 论文，它们不太喜欢大段抒情，更像是“现实问题 → 为什么旧方法不行 → 新方法如何补洞 → 用什么证据证明”。这就是为什么读起来会很“硬”，但也很有说服力。
九、如果你想直接模仿，我建议你学这 8 条
1. 标题用“方法名 + 冒号 + 功能描述”。
2. 第一页一定放一张能同时讲问题、方法、结果的大图。
3. Abstract 里必须出现“真实瓶颈”，不要只写“improves performance”。
4. Introduction 第二段把 limitation 编号化，越具体越好。
5. 第三段先给 research question 或 key insight，再讲方法。
6. Contributions 固定三点，别写散。
7. Experiments 不只报分，还要报 cost、效率、泛化、兼容性。
8. 如果是系统/agent 论文，方法节一定写 inference-time 怎么用；如果是纯 method 论文，最好先来一个 empirical motivation。
十、最后一句判断
它们都非常擅长把“我做了什么”写成“这个领域为什么现在就需要这个东西，而且只有我这样写，整件事才完整”。 这就是它们最值得学的地方。
我建议你至少先对下面这些问题心里有数。

- 问题的输入是什么？
- 输出是什么？
- 难点来自哪里？

2. 旧方法到底哪里不行，具体到 failure mode 是什么？
这个问题特别重要，因为这些示例最强的地方之一，就是不会泛泛地说“existing methods still face challenges”，而是会拆成具体 failure modes。agent 写作偏好里直接把这点总结出来了：memory 太粗糙、evaluator 太贵、reward 太稀疏、小模型会 hallucinate、闭源系统不可复现，这些都属于 reviewer 一眼能懂的硬伤。
所以你要提前回答：
- 你打的是谁？
- 他们的主要短板是机制上的，还是数据上的，还是评测上的？
- 这些短板会导致什么后果？
- 有没有一个具体案例能证明这个痛点不是抽象存在？
G-Memory 的写法很值得学：它不是说“MAS memory 还有待提升”，而是明确指出两点——现有机制过于简单，忽视复杂协作轨迹；缺乏 cross-trial 和 agent-specific customization。引言继续追问：为什么不能直接把 single-agent memory 搬到 MAS？因为 MAS 轨迹更长、token 成本更高、直接塞长上下文没用。这个“追问式拆痛点”的方式很强。

3. 你的方法到底是什么，而不是什么？
这听起来简单，但其实很多论文写崩就是因为这个边界没想清楚。
在这些示例里，方法定义都很清晰：
- G-Memory 是一个 hierarchical agentic memory architecture；
- Web-Shepherd 不只是一个模型，而是 PRM + collection + benchmark；
- OpenCUA 更不是单一模型，而是一整套开放框架；
- graph 风格里则通常是某种 jointly / iteratively optimize 的 method/framework。
所以你要先回答：
- 你的工作是 algorithm、framework、system、benchmark、dataset，还是它们的组合？
- 你最核心的创新单位是什么？
- 你的论文主角是一条理论结果、一个机制、一个 stack，还是一个完整 pipeline？
- 你不做什么？不解决什么？
这个“不做什么”非常关键。因为如果你边界不清，reviewer 很容易拿你没打算解决的问题来质疑你。
答：不是单一全信息或者全unshared，而是混合的多级系统算法
4. 你的 key insight 是什么？为什么你的设计不是拍脑袋？
好论文不是只说“我们提出方法 X”，而是会告诉你：
“我们的关键观察是 Y，所以自然导致设计 Z。”
graph 写作偏好里非常强调这一点：第三段要写 Our key insight lies in ...，method 部分也要从 insight 过渡到具体机制。
你要先想明白：
- 你的方法背后有没有一个结构性观察？
- 这个观察能不能不用公式也讲清楚？
- 它能不能解释“为什么是这个模块组合，而不是别的”？
如果你的工作是 PS / Risky-PS 这类，更要提前想清：
- 你的 share / unshare / risky / safe 这些概念的“语义判据”是什么？
- 它们在 agent 映射里分别对应什么现实约束？
- 为什么这个映射不是任意发明的，而是跟反馈结构或信息暴露机制一致？

5. 你的最小论文故事线是什么？
这些示例都不是随机堆内容，而是有很稳的 story arc。
graph 偏好总结里，正文结构通常是 Abstract → Introduction → Problem Formulation →（可选）Empirical Study → Methodology → Experiments → Conclusion；agent 风格则更常是 Abstract → Introduction → Related Work → Preliminaries → Method → Experiments。
所以你要提前决定：
- 你这篇更偏 agent/system，还是更偏 method/theory？
- Related Work 放正文还是附录？
- 你要不要单独来一个 motivation/empirical study？
- 你的 story 是“问题诊断 → 方法 → 实验”，还是“理论动机 → 算法 → 界 → 实验”？
如果这一步没想清，写到一半就会不断挪章节，最后整篇结构会很乱。

这是写前必须想清楚的，不然实验设计会反过来绑架写作。

- 你的主 claim 是什么？
- 每个 claim 需要什么证据来支撑？
- 哪些证据是主实验，哪些是辅助实验？

- Q4 超参数敏感性
- Q5 效率分析
- Q6 鲁棒性分析。

7. 你的 baseline 集合是否足够“公平且有说服力”？
这批论文还有个共同特点：很重视 positioning。agent 风格特别强调 Related Work 不能只是流水账，要分子方向，并且最后一句通常要写 “Unlike prior work, we ...”。
所以你写前就要想好：
- 你要比的 baseline 分哪几类？
- 每一类 baseline 为什么必须出现？
- 哪一个是最难打的、最关键的 strong baseline？
- 你的 setting 对 baseline 是否公平？
- 有没有 baseline 因为环境/资源限制跑不了，那你怎么解释？
如果 reviewer 看完会问“为什么不跟 X 比”，那你最好在开写前就知道答案。
8. 你的实验设定有没有“最小闭环”？
agent/system 论文很强调闭环，不是只讲一个 module，而是 method、data、benchmark、cost、deployment value 一起讲。agent_writing_preference.md 明确把这点列为总体观察。
所以你得先想：
- 你的工作只提出方法，还是要连 evaluator / benchmark / task family 一起定义？
- 如果是系统问题，你是不是也需要补一个实验协议，甚至数据构建方式？
- 如果你说自己更 practical，那有没有 cost / token / runtime 指标？
- 如果你说自己更 general，那有没有 cross-domain / OOD / multiple families 的实验？
G-Memory 的贡献总结就很典型：不是只说性能涨了，还强调 plug-and-play、token 可控。
9. 你的 main result 到底想让读者记住哪 1–3 个数字？
agent 摘要偏好里写得很清楚：摘要和实验都要给最有冲击力的数字，而不是一堆平均结论。
你开写前就该知道：
- 你最想在摘要里放哪 1–3 个数字？
- 哪个结果最能定义这篇论文的价值？
- 是性能提升、成本下降、regret 改善，还是开放基础设施规模？
如果你现在都挑不出 1–3 个“论文代表数字”，那大概率说明主线还没收束。
10. 你的论文 scope 到底有多大，哪些 claim 不能说过头？
这个问题非常重要，而且常被忽略。
Web-Shepherd 的 checklist 片段里有个 reviewer 视角特别值得记：摘要和引言里的 claims 必须和理论、实验结果严格匹配，也要反映结果能推广到什么范围；如果 assumptions 和 limitations 没说清，reviewer 不会喜欢。
所以你必须提前想：
- 你的结果只在某个 family / environment / benchmark 上成立，还是更普遍？
- 你的理论是不是依赖强假设？
- 你的 agent 映射是不是只适用于固定树 / 终局 cost / 某类 task templates？
- 你的系统是否依赖某个 backbone、某类 evaluator、某个数据源？
如果这些边界不先想清，写摘要和引言时特别容易把话说大。
11. 你的“为什么是现在”是否成立？
NeurIPS 论文很吃这个：不是只有“有趣”，还要有“timely”。
agent 偏好里提到，这类论文通常会在引言里强调为什么 current evaluator / memory / reward / openness 不适用，并且会在第一页就通过大图、性能/成本 teaser 建立紧迫感。
你要想：
- 为什么这个问题在 2025–2026 的社区里是 hot 的？
- 你的工作踩中了哪条主线：memory、trajectory/behavior distillation、reward modeling、search/self-improvement、computer-use foundation，还是别的？
- 你是在补一块缺失的基础设施，还是提出一个对现有方向有解释力的新框架？
如果“为什么是现在”讲不出来，文章就容易显得像旧问题换壳。
12. 你准备把论文写成哪一种风格？
从你前面看的材料看，其实有两种主风格：
一种是 agent / infrastructure + method 风格：更强调系统闭环、practicality、benchmark 生态、第一页大图、正文保留 Related Work。
另一种是 graph / method 风格：更强调 Problem Formulation、动机实验、方法结构、实验问题化组织、附录完整。
你最好提前决定自己更像哪一种，因为这会影响：
- 摘要语气
- 引言写法
- Related Work 放哪
- 方法的讲法
- 实验怎么排
- 附录怎么组织
13. 如果只压缩成最核心的 10 个 pre-write 问题
你可以直接把这 10 个问题贴到文档顶部，开写前逐个回答：
1. 我的论文要解决的最小核心问题是什么？
2. 旧方法最关键的 2–3 个 failure mode 是什么？
3. 我的工作本质上是 algorithm、framework、system、benchmark 还是组合？
4. 我的 key insight 是什么？
5. 我的方法边界是什么，不解决什么？
6. 我的主 claim 有哪几个？
7. 每个主 claim 对应哪条实验或理论证据？
8. 哪些 baseline 必须出现，为什么？
9. 摘要里最该出现的 1–3 个数字是什么？
10. 我的方法适用范围和 limitations 是什么？
如果这 10 个问题你都能回答得很稳，真正动笔时就会顺很多。

## 14. 我对你最直接的建议

我最直接的建议还是这三条：

### 第一

**把主问题写成“反馈结构”问题，而不是“agent benchmark”问题。**
不然 reviewer 会觉得你像是“有个算法，硬找个 agent 场景放进去”。

### 第二

**让 full-share 成为故事中间桥梁，而不是一个普通 baseline。**
因为它的作用是告诉读者：如果共享是完全允许的，理论上能买到什么；Barrier-PS 正是对这个理想情形的现实化。

### 第三

**所有实验都要服务于同一个故事：**
[
\text{bandit} \rightarrow \text{full-share} \rightarrow \text{barrier} \rightarrow \text{agent workflow}
]
而不是变成“理论一套、agent 一套、仿真一套”。
你现在已经把实验表按这个逻辑排出来了，这是很好的。
